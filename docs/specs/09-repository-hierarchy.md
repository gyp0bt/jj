# レポジトリ階層制約 仕様書

## 1. 概要

本仕様は、jjプロジェクトのグラフデータモデルにレポジトリ階層制約を導入する破壊的変更を定義します。

### 目的

- グラフ内の全ノードに明確な所有関係（帰属先）を定義
- レポジトリをツリー構造で管理し、ルートレポジトリを頂点とする階層を構築
- ノードの孤立を防止し、データの一貫性を保証

### 制約ルール

1. **レポジトリ以外のノード**は、いかなるtypeであってもレポジトリの下にしか存在できない
2. **レポジトリ**はレポジトリの下にしか存在できない（ルートレポジトリを除く）
3. システムには**ルートレポジトリ**が1つ存在する
4. **上下関係の定義**: ルートレポジトリからの関係距離が近い方を「上」、遠い方を「下」とする

## 2. データモデル変更

### 2.1 新しいノードタイプ: `repository`

| フィールド | 値 | 説明 |
|-----------|-----|------|
| `type` | `"repository"` | レポジトリノード |
| `name` | ディレクトリ名 | レポジトリのディレクトリ名 |
| `format` | `"repository"` | 固定値 |
| `properties.path` | 相対パス | ルートからの相対パス（ルートは `"."`) |
| `properties.is_root` | `"true"` / `"false"` | ルートレポジトリかどうか |
| `properties.depth` | `"0"`, `"1"`, ... | ルートからの深さ |

### 2.2 新しいリレーション: `belongs_to`

| フィールド | 説明 |
|-----------|------|
| `label` | `"belongs_to"` |
| `node1_id` | 子ノード（帰属する側）のID |
| `node2_id` | 親レポジトリのID |

**方向性**: 子 → 親（下 → 上）

### 2.3 レポジトリ間の親子関係

レポジトリ同士の親子関係も `belongs_to` で表現する。

```
Root Repository (depth=0)
├── belongs_to ← Sub-Repository A (depth=1)
│   ├── belongs_to ← Node (go_idx1.inp)
│   └── belongs_to ← Sub-Repository A1 (depth=2)
│       └── belongs_to ← Node (go_idx2.inp)
└── belongs_to ← Node (material.inp)
```

## 3. ルートレポジトリ

### 3.1 定義

- `parse_project()` の対象ディレクトリ（`project_root`）がルートレポジトリとなる
- ルートレポジトリは `properties.is_root = "true"` を持つ
- ルートレポジトリは `belongs_to` 関係の親を持たない唯一のノード

### 3.2 自動生成

```python
Node(
    id=<auto>,
    type="repository",
    name=project_root.name,
    format="repository",
    properties={
        "path": ".",
        "is_root": "true",
        "depth": "0",
    },
)
```

---

## 4. サブレポジトリの検出

### 4.1 検出基準

サブレポジトリは以下の基準で検出される:

- `.jj/` ディレクトリを含むサブディレクトリ
- 将来的に設定ファイルで明示的に指定可能

### 4.2 ノードの帰属先決定ルール

各ノードは**最も近い祖先レポジトリ**に帰属する:

1. ノードのパスから親ディレクトリを辿る
2. 最初に見つかったレポジトリがそのノードの帰属先
3. サブレポジトリが見つからない場合はルートレポジトリに帰属

---

## 5. バリデーション

### 5.1 グラフ整合性チェック

`GraphModel` に以下のバリデーションを追加:

1. **帰属チェック**: 全非レポジトリノードが `belongs_to` 関係を持つこと
2. **レポジトリ帰属チェック**: ルート以外の全レポジトリが `belongs_to` 関係を持つこと
3. **帰属先タイプチェック**: `belongs_to` の `node2_id` が必ず `type="repository"` であること
4. **ルート一意性**: `is_root="true"` のレポジトリが正確に1つであること
5. **循環参照禁止**: `belongs_to` 関係に循環がないこと

### 5.2 バリデーションAPI

```python
class GraphModel(BaseModel):
    def validate_repository_hierarchy(self) -> list[str]:
        """レポジトリ階層の整合性を検証し、エラーメッセージのリストを返す"""
        ...
```

## 6. GraphService への影響

### 6.1 parse_project() の変更

1. **最初のステップ**: ルートレポジトリノードを生成
2. **サブレポジトリ検出**: `.jj/` を含むサブディレクトリをスキャン
3. **belongs_to 構築**: 全ノードに対して最寄りの親レポジトリを決定
4. **バリデーション**: 生成後にグラフの整合性をチェック

### 6.2 処理順序

```
1. ルートレポジトリノード生成
2. サブレポジトリ検出・ノード生成
3. ファイルスキャン・ノード生成（既存）
4. リレーション構築（既存）
5. belongs_to 関係構築（新規）
6. バリデーション（新規）
```

---

## 7. 既存機能への影響

### 7.1 summary()

- `nodes_by_type` に `"repository"` が追加される
- `relations_by_label` に `"belongs_to"` が追加される

### 7.2 Obsidianエクスポート

- レポジトリノードはエクスポート対象外（または専用テンプレート）
- `belongs_to` 関係はfrontmatterの `repository` プロパティとして反映

### 7.3 既存テスト

- `parse_project()` の戻り値に新しいノード・リレーションが追加されるため、カウント系のテストに影響
- 全テストで `repository` ノードと `belongs_to` 関係のフィルタリングが必要
