## 設計思想

### プロジェクトの概要とゴール
- CAE業務向けの材料/案件/タグと関連ドキュメントを、検索・閲覧・入出力できる軽量なデータベースを提供する。
- CAE業務チームが10人規模で利用する材料物性、案件と、それに関連するドキュメントの入出力が運用できるアプリ開発。
- 運用の中心は「入れる/出す」。UIはNext.jsで軽快に、重いロジックは後で分離可能な構造にする。
- 現状：ロードマップ3（操作性の調整）を進行中。ラベル付きRelation、インポート編集機能まで完了。
- ゴール：データ型の整備、一括エクスポート、import/exportの充実

## Import / Export 仕様（設計案）

### 目的
- **ドラッグ&ドロップ主体**で多様なデータを取り込み、将来の水平展開が容易な構造を定義する。
- Next.jsのUIロジックと複雑な解析ロジックを分離し、**軽量な運用**と**拡張性**を両立する。

### 基本方針
1. **Next.jsは即時インポートする**
   - フォルダ/zipを受け取り、その場でplaceholderを生成して検索体験に反映する。
   - 受払いフォルダ運用はしない（NG）。
2. **高次の解析はprefect側**
   - Next.jsは基礎ルールで読み取り、prefectは高度な解析・補正を担当する。
3. **インターフェースはYAMLで契約**
   - すべての実装をYAMLに閉じ込めない。
   - **インターフェースのみYAML化**し、内部実装は自由。

### 用語
- **インポートスキーマ**: ファイル種別/中身/パターンから属性やタグを抽出するルールの単位。
- **Placeholder**: 解析時に確定しない構造・属性・タグを一時的に保持する表現。
- **StringEntity**: Material/Project/Tagなどの主レコード。

### 入力（Import）仕様

#### 1) ドラッグ&ドロップの前提
- **Windowsでフォルダ/zipをドロップ**が主戦場。
- その場で階層構造を読み取り、placeholderを生成してUIへ反映する。
- フォルダ自体もStringEntityとして登録する（type=directory）。

#### 2) 階層 → Relation への読み替え（Next.jsで実施）
- フォルダ階層は Relation としてPlaceholder化する。
- **フォルダは `type=directory`、子フォルダは `label=child`**。
- 子ファイルは `label=null` または `label=contains` とする。

#### 3) 拡張子とスキーマ補正（Next.jsで実施）
- ファイルは拡張子からフォーマットを列挙型で一致判定する。
- その結果をplaceholderに反映し、ユーザーがUI（テーブル/ダイアグラム/グラフ）で修正できる。

#### 4) 分割・マージの前提
- 1ファイル = 1 StringEntity ではない。
- 例:
  - INPの `material` ブロック単位で分割
  - Markdownのブロック単位で分割
  - 任意単位でのマージも許可
  - ただし**Next.jsで即時にやるのは最小限**、詳細はprefect側で処理する

#### 5) YAMLによる補正ルール（Next.jsで実施）
- ユーザーが**関係やプロパティをYAMLで整形**しておく。
- ファイル名の一致判定でYAMLを探し、ヒットしたらplaceholderを修正/タグ追加。
- YAML以外（csv/xlsx/json/md等）の内容は、**必ずYAMLに変換してから**使う。

### エクスポート（Export）仕様
- **Relationを含むデータはフォルダin/out**を基本とする。
- `attached_documents` が無い材料データの INP body は単一ファイル形式を継続。
- 「業務フォルダをzip化して投げると必要ファイルだけ抽出」できる状態を目標とする。
- エクスポート時は、入力と同等または**より整理されたフォルダ構造**を指向する。
- 将来的にはテンプレート出力（markdown/html/yaml）も提供したい。

### 仕様の最小スキーマ（YAML契約）
> 目的: 後続ロジックが致命的に破綻しないための最低限。

```yaml
version: 0.1
batch:
  id: "import-2026-01-31-001"
  source:
    type: "drag_and_drop" # drag_and_drop | api
    os: "windows"
  received_at: "2026-01-31T00:00:00Z"
items:
  - path: "projectA/materials/steel/"
    kind: "folder" # file | folder
    entity_type: "directory"
    schema_keys: ["folder/directory"]
    placeholders:
      props:
        sys: {}
        user: {}
      tags:
        sys: ["directory"]
        user: []
  - path: "projectA/materials/steel/steel.inp"
    kind: "file" # file | folder
    mime: "text/plain"
    schema_keys: ["inp/material-block"]
    placeholders:
      props:
        sys:
          format: "inp"
          basename: "steel"
        user: {}
      tags:
        sys: ["material"]
        user: []
relations:
  - type: "folder-structure"
    from: "projectA"
    to: "projectA/materials/steel"
    label: "child"
  - type: "file-structure"
    from: "projectA/materials/steel"
    to: "projectA/materials/steel/steel.inp"
    label: "contains"
notes:
  - "解析ロジックはprefect側で拡張する"
```

### スキーマ設計の意図
- **items**: 受払い対象の一覧。ファイル/フォルダ両方を扱う。
- **schema_keys**: インポートスキーマの識別子（増減可能・一覧性確保）。
- **placeholders**: プロパティ/タグ/関係の仮置き。
- **relations**: 階層や同一basename対応などの仮Relationを記録。

### Import/Export ロードマップ（優先順位つき）
> データ堅牢性は後回し。ただし後工程で致命的にならない範囲でスキーマの芯を作る。

- [x] (P0) フォルダ/ファイルのドラッグ&ドロップ受け渡しを成立
- [x] (P0) **最小スキーマ**をYAML契約として固定し、prefect側が参照できる状態にした
- [x] (P1) `schema_keys` を一覧化できる管理ドキュメントを追加 → [schema-keys.md](schema-keys.md)
- [x] (P1) 典型パターン（yaml/json/inp/markdown）から属性抽出の起点を決める → [attribute-extraction.md](attribute-extraction.md)
- [ ] (P2) ブロック単位分割（INP/material、Markdown/heading）を追加
- [ ] (P2) 任意単位マージは「ユーザー操作 or ルール」のどちらで行うかを整理
- [ ] (P3) フォルダ構造の正規化と、テンプレート出力（markdown/html/yaml）を試験導入
- [ ] (P4) 受払いYAMLのスキーマ検証を導入（軽量なチェックから）
- [ ] (P4) 破損時の退避/復旧ルールを用意

- **UI側の複雑化**: UIは受払いのみとし、解析ルールはprefectへ委譲。

## Core Data Model

```typescript
// src/lib/types.ts
type EntityType = "Material" | "Project" | "Tag";

type StringEntity = {
  id: string;
  name: string;
  body: string;
  entityType?: EntityType | null;
  sysTags: string[];
  userTags: string[];
  sysProps: Record<string, string>;   // format, extension等
  userProps: Record<string, string>;
  attachedDocuments?: AttachedDocument[];
  remark?: string | null;
  domain?: string | null;
  domainSource?: "user" | "auto" | "curation" | null;
  domainConfidence?: number | null;
  createdBy?: string | null;
  createdAt: string;
  updatedAt: string;
};

type Relation = {
  id: string;
  label: string;
  entity1Id: string;
  entity2Id: string;
  createdAt: string;
};

type Document = {
  id: number;
  name: string;
  relativePath: string;
  mimeType?: string | null;
  size?: number | null;
  description?: string | null;
  createdBy?: string | null;
  createdAt: string;
  updatedAt: string;
};

type AttachedDocument = {
  relativePath: string;
  documentId: number;
};
```

## DBスキーマ

```sql
CREATE TABLE entities (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  body TEXT NOT NULL,
  sys_tags TEXT NOT NULL DEFAULT '[]',      -- JSON配列
  user_tags TEXT NOT NULL DEFAULT '[]',     -- JSON配列
  sys_props TEXT NOT NULL DEFAULT '{}',     -- JSONオブジェクト
  user_props TEXT NOT NULL DEFAULT '{}',    -- JSONオブジェクト
  remark TEXT,
  domain TEXT,
  domain_source TEXT,                       -- 'user' | 'auto' | 'curation'
  domain_confidence REAL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

```bash
curl -X POST http://localhost:3000/api/entities/seed \
  -H "Content-Type: application/json" \
```

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/entities/seed -ContentType "application/json" -Body '{"source":"mock"}'
```

```bash
rm -rf data/mat-db.sqlite
```

- DBファイルは `.gitignore` 済み
- スキーマは `db.ts` の `initSchema()` で自動作成

## Development Flow

### コンポーネント実装手順

```
1. ユーザーが仕様を記述（チャット）
2. AIが src/components/ComponentName/README.md に仕様書保存
3. AIが src/components/ComponentName/index.tsx を実装
4. プレビュー追加 → src/app/dev/components/page.tsx
5. ユーザー確認 → http://localhost:3000/dev/components
6. 必要に応じてロジック追加 → 再確認
7. 全コンポーネント完成後 → ページにassemble
```

### 仕様書フォーマット（README.md）

```markdown
# ComponentName

## 概要
[1-2行の説明]

## Props
| Prop | Type | Default | Description |
|------|------|---------|-------------|

## Variants / States
[variant, size, disabled等]

## Events
[onClick, onChange等]

## 備考
[実装上の注意点]
```

### 仕様書の置き場
- 原則として仕様書は対象ファイルと同一階層の `README.md` に保存する。
- 例: `src/components/Button/README.md`、`src/app/search/README.md`、`src/lib/README.md`

### 仕様書の更新タイミング
1. 新しいタスク開始時に必ずユーザーとの問答を経て、その後に仕様書を更新する。
2. 仕様書更新後に実装し、実装後に再度仕様書を更新する。
3. その後のユーザー確認を経て、追加事項があれば仕様書を更新する。

### 軽量ロジック判断基準
以下に該当する場合、UI実装と同時にロジックも実装：
- useState 1-2個
- 外部API呼び出しなし
- 副作用（useEffect）が単純または不要
