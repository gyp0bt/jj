## 設計方針

### 目的
検証中盤から本番環境にかけて、バックエンドをneo4jに移行し、「neo4jデスクトップの業務ドメイン特化版」を実現する。Cypherライクな柔軟なグラフデータ検索と、多様なビューでグラフデータの直感的入出力を可能にする。

### ビジョン
1. **neo4jグラフDB移行** — SQLiteからneo4jへ段階的に移行し、グラフネイティブなデータモデルを活用
2. **Cypherライククエリ** — ユーザーがCypherに似た直感的構文でグラフデータを検索・フィルタリング
3. **多様なビュー統合** — テーブル/カード/グラフ/ダイアグラムを「真実のソース」であるテーブルビューを基盤として統合
4. **視覚的階層化** — edgeラベルを使ったダイアグラムビューでの視覚的部分階層化（目玉機能）
5. **フォーカスナビゲーション** — shift+enterで対象エンティティを中心としたビュー切り替え、親等数設定による範囲指定

## 技術的考慮事項

### neo4j移行のメリット
- **ネイティブグラフ構造**: Relation（エッジ）がファーストクラスエンティティとして扱われる
- **Cypher言語**: 直感的なグラフクエリ言語で複雑な関係性検索が容易
- **GDSライブラリ**: 最短経路、中心性、コミュニティ検出などのグラフアルゴリズムが利用可能
- **可視化との親和性**: neo4j Bloomとの連携、あるいは独自ビューアの構築

### 移行戦略
1. **Phase 4-A/4-B**: 現在のSQLite基盤でUI/UXを完成させる
2. **Phase 4-C**: SQLite上でCypherライク構文をエミュレート実装
3. **Phase 4-D**: neo4jへの実際の移行（オプショナル、本番運用時に検討）

### データモデル対応

| 現在（SQLite） | neo4j移行後 |
|---------------|------------|
| `entities` テーブル | `(:Entity)` ノード |
| `relations` テーブル | `-[:RELATION {label}]->` エッジ |
| `userProps` JSONカラム | ノードプロパティ |
| `sysTags` 配列 | ノードラベル または プロパティ |

## Cypherライククエリ構文（案）

```cypher
// 基本検索
MATCH (e:Entity) WHERE e.domain = 'steel' RETURN e

// Relation経由の検索
MATCH (e1:Entity)-[r:contains]->(e2:Entity)
WHERE e1.name CONTAINS 'project'
RETURN e1, r, e2

// 親等数指定
MATCH path = (e:Entity {name: 'Steel-A'})-[*1..3]-(connected)
RETURN path

// ラベル階層化
MATCH (parent)-[:child]->(child)
WHERE parent.sysTags CONTAINS 'directory'
RETURN parent, collect(child) AS children
```

## 視覚的部分階層化（目玉機能）

### 概要
ダイアグラムビューで、特定のRelationラベル（例: `child`, `contains`, `belongs_to`）を持つエッジを「階層関係」として解釈し、視覚的にグループ化・ネスト表示する。

### 動作仕様
1. **階層ラベル設定**: ユーザーが「階層として扱うRelationラベル」を設定（デフォルト: `child`, `contains`）
2. **自動グルーピング**: 設定されたラベルのエッジで接続されたノードを親子関係として可視化
3. **ネスト描画**: 親ノードの内部に子ノードを含む形で描画（コンテナボックス風）
4. **折りたたみ**: 親ノードを折りたたむと子ノードを非表示に

### 例
```
[Project-A]
├─ [materials/]
│   ├─ [steel.inp]
│   └─ [aluminum.inp]
└─ [docs/]
    └─ [README.md]
```
上記のフォルダ構造を、ダイアグラムでネストされたボックスとして表現。
